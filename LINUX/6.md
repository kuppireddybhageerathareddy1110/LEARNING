## 3. What is the difference between a Hard Link and a Soft Link?

| Hard Link                              | Soft Link                          |
| -------------------------------------- | ---------------------------------- |
| Points to inode                        | Points to filename                 |
| Works even if original file is deleted | Breaks if original file is deleted |
| Cannot cross filesystems               | Can cross filesystems              |
| Cannot link directories (normally)     | Can link directories               |

# Git – In Depth for SRE Interviews

## What is Git?

**Git** is a distributed version control system (DVCS) used to track changes in source code and collaborate with multiple developers.

Created by Linus Torvalds in 2005.

### Why Git?

Before Git:

* Developers manually shared code.
* Difficult to track changes.
* No easy rollback mechanism.
* Collaboration caused conflicts.

Git solves these problems by:

* Tracking every change.
* Maintaining version history.
* Supporting multiple developers.
* Allowing rollback to previous versions.
* Managing branches for new features.

---

## Version Control System (VCS)

A VCS records changes to files over time.

Example:

Version 1:

```python
print("Hello")
```

Version 2:

```python
print("Hello World")
```

Git stores both versions and lets you switch between them.

# 1. git cherry-pick

## What is it?

`git cherry-pick` copies **one or more specific commits** from one branch and applies them to another branch.

Unlike `git merge`, it does **not** merge the entire branch.

### Example

```
main
 |
 A---B---C

feature
 |
 A---B---D---E
```

Suppose you only want commit **D**.

```
git checkout main
git cherry-pick <commit-id-of-D>
```

Result:

```
main
 |
 A---B---C---D

feature
 |
 A---B---D---E
```

Only **D** is copied.


* Copy only a bug fix.
* Avoid merging unfinished work.
* Apply production hotfixes.
* Recover lost commits.

# Topic 1: Linux Boot Process (In Depth)

## Interview Question

**Q: Explain the Linux boot process from power-on until the login prompt appears.**

---

# Overview

The Linux boot process is the sequence of steps that starts when you press the power button and ends when the system is ready for users.

```
Power On
    │
    ▼
BIOS / UEFI
    │
    ▼
Bootloader (GRUB)
    │
    ▼
Linux Kernel
    │
    ▼
initramfs (Initial RAM Filesystem)
    │
    ▼
systemd (PID 1)
    │
    ▼
System Services
    │
    ▼
Login Prompt / GUI
```

---

# Step 1: Power On

When you press the power button:

* CPU resets.
* RAM is initialized.
* Hardware begins startup.
* Control is given to the motherboard firmware.

The firmware is either:

* BIOS (older systems)
* UEFI (modern systems)

---

# Step 2: BIOS

**BIOS (Basic Input/Output System)** is firmware stored on the motherboard.

### Responsibilities

* Perform POST (Power-On Self-Test).
* Detect CPU, RAM, keyboard, disks, and other hardware.
* Check the boot order (SSD, HDD, USB, Network).
* Load the bootloader from the selected boot device.

If hardware fails, BIOS may stop the boot process and emit beep codes or display an error.

---

# Step 3: UEFI

Most modern systems use **UEFI (Unified Extensible Firmware Interface)** instead of BIOS.

Advantages:

* Faster boot.
* Supports disks larger than 2 TB.
* Secure Boot support.
* Better graphical interface.
* GPT partition support.

Instead of loading boot code from the MBR, UEFI loads an `.efi` bootloader from the EFI System Partition (ESP).

---

# BIOS vs UEFI

| BIOS                   | UEFI                            |
| ---------------------- | ------------------------------- |
| Older firmware         | Modern firmware                 |
| Uses MBR               | Uses GPT                        |
| Limited to ~2 TB disks | Supports much larger disks      |
| Text interface         | Can support graphical interface |
| Slower                 | Faster                          |
| No Secure Boot         | Supports Secure Boot            |

---

# Step 4: Bootloader (GRUB)

GRUB stands for **GRand Unified Bootloader**.

Its job is to load the Linux kernel.

GRUB:

* Displays the boot menu.
* Lets you choose an operating system (Linux, Windows, etc.).
* Lets you choose an older kernel if needed.
* Passes boot parameters to the kernel.

Typical configuration files:

```
/boot/grub/grub.cfg
/etc/default/grub
```

Useful commands:

```bash
cat /proc/cmdline
```

Shows the kernel boot parameters.

---

# Step 5: Linux Kernel

The kernel is the core of the operating system.

Responsibilities:

* Initialize CPU scheduling.
* Detect and initialize hardware.
* Load device drivers.
* Mount the root filesystem.
* Start the first userspace process.

Useful command:

```bash
uname -r
```

Shows the running kernel version.

---

# Step 6: initramfs

**initramfs (Initial RAM Filesystem)** is a temporary root filesystem loaded into memory before the real root filesystem.

Why is it needed?

The kernel may not yet have the drivers needed to access the root disk. `initramfs` contains essential drivers and tools to:

* Load storage drivers.
* Locate the real root filesystem.
* Mount it.
* Hand control over to it.

If `initramfs` fails, you may see an emergency shell or a "kernel panic."

---

# Step 7: systemd (PID 1)

Once the real root filesystem is mounted, the kernel starts **systemd**.

`systemd` is the first userspace process and always has **PID 1**.

Check it:

```bash
ps -p 1
```

Example output:

```
PID TTY          TIME CMD
1   ?        00:00:05 systemd
```

Responsibilities:

* Start system services.
* Mount filesystems.
* Manage networking.
* Handle logging.
* Manage system targets (runlevels).

---

# Step 8: Services Start

`systemd` starts essential services such as:

* SSH server
* Network manager
* Cron scheduler
* Logging service
* Web server (if enabled)

Useful command:

```bash
systemctl list-units --type=service
```

---

# Step 9: Login Prompt

Finally:

* Console login (`getty`) starts on terminals.
* Or the graphical display manager starts (GNOME, KDE, etc.).

The system is now ready for users.

---

# What is systemd?

**systemd** is the default **system and service manager** in most modern Linux distributions (Ubuntu, RHEL, CentOS, Debian, etc.).

It is the **first userspace process** started by the Linux kernel.

Its **Process ID (PID)** is always **1**.

# Responsibilities of systemd

* Starts all system services.
* Stops services.
* Restarts failed services.
* Manages dependencies.
* Mounts file systems.
* Starts networking.
* Starts SSH.
* Collects logs through journald.
* Handles shutdown and reboot.

Without systemd, the OS would not automatically start essential services.

# Common Interview Questions

### Q1. Difference between Process and Thread?

| Process                    | Thread                |
| -------------------------- | --------------------- |
| Independent execution unit | Part of a process     |
| Separate memory            | Shared memory         |
| Higher overhead            | Lightweight           |
| Communication via IPC      | Direct memory sharing |

### Q2. Difference between `kill` and `kill -9`?

* `kill` sends **SIGTERM (15)**, allowing the process to clean up and exit gracefully.
* `kill -9` sends **SIGKILL (9)**, which immediately terminates the process. It cannot be caught or ignored.

---

### Q3. What is a Zombie process?

A process that has finished execution, but whose parent has not yet read its exit status. It appears with state `Z`.

---

### Q4. What is the difference between `ps`, `top`, and `htop`?

| Command | Purpose                                               |
| ------- | ----------------------------------------------------- |
| `ps`    | Snapshot of current processes                         |
| `top`   | Real-time process monitoring                          |
| `htop`  | Interactive real-time monitor with a richer interface |

---

### Q5. What is the difference between `pkill` and `pgrep`?

* `pgrep` finds process IDs by name.
* `pkill` sends a signal (by default, SIGTERM) to matching processes.

# What is Memory?

Memory (RAM) is temporary storage used by the CPU to execute programs quickly.

Example:

```text
Hard Disk (Persistent)
        ↓
Program Loaded
        ↓
RAM
        ↓
CPU Executes Instructions
```

Unlike disk storage, RAM is **volatile**, meaning its contents are lost after a reboot.

# Types of Memory in Linux

```text
+-----------------------+
| Physical RAM          |
+-----------------------+
          ↓
+-----------------------+
| Buffers              |
+-----------------------+
          ↓
+-----------------------+

+-----------------------+
          ↓
+-----------------------+

+-----------------------+
```

---

# Physical Memory (RAM)

This is the actual hardware memory installed in the system.

Example:

```text
Installed RAM = 16 GB
```

Applications such as:

* Java
* Python
* Nginx
* MySQL

all use RAM.

Check total RAM:

```bash
free -h
```

---

# Virtual Memory

Virtual memory allows processes to use more memory than the available physical RAM.

It combines:

* RAM
* Swap space

Example:

```text
RAM = 8 GB
Swap = 4 GB

Virtual Memory = 12 GB
```

---

# Swap Memory

Swap is disk space used when RAM becomes full.

```text
RAM Full
      ↓
Inactive Pages
      ↓
Move to Swap
```

Swap is **much slower** than RAM because it resides on disk.

Check swap:

```bash
swapon --show
```

or

```bash
free -h
```

Example:

```text
Swap:
4G total
1.5G used
2.5G free
```

---

# Buffers

Buffers temporarily store data during I/O operations.

Example:

Copying a large file:

```bash
cp movie.iso /backup/
```

Linux uses buffers while writing to disk.

---

# Cache

Linux caches frequently accessed files in RAM to improve performance.

Example:

Reading:

```bash
cat largefile.log
```

The second read is faster because the data is served from cache.

**Important Interview Point:**

Linux intentionally uses free RAM as cache. High memory usage does **not** necessarily mean there is a problem.

---

# Memory Layout

```text
+---------------------+
| Application Memory  |
+---------------------+
| Shared Libraries    |
+---------------------+
| Heap                |
+---------------------+
| Stack               |
+---------------------+
```

| Stack                                     | Heap                                |
| ----------------------------------------- | ----------------------------------- |
| Stores function calls and local variables | Stores dynamically allocated memory |
| Automatically managed                     | Manually or garbage-collected       |
| Smaller                                   | Larger                              |
| Faster                                    | Slower                              |

# OOM Killer (Out Of Memory Killer)

If the system runs out of memory and cannot allocate more, the Linux kernel invokes the **OOM Killer**.

It terminates one or more processes to free memory.

Check logs:

```bash
dmesg | grep -i oom
```

or

```bash
journalctl | grep -i oom
```

Example:

```text
Out of memory:
Killed process 2345 (java)
```

---

# Memory Leak

A memory leak occurs when a program allocates memory but never releases it.

Symptoms:

* Memory usage steadily increases.
* Restarting the application temporarily fixes the issue.
* Eventually the OOM Killer may terminate the process.

Example:

```text
10 AM → 2 GB
11 AM → 4 GB
12 PM → 7 GB
```

---

# Thrashing

Thrashing occurs when the system spends more time swapping memory than executing processes.

```text
RAM Full
      ↓
Swap Used Heavily
      ↓
CPU Waits
      ↓
System Becomes Slow
```

Symptoms:

* High swap usage
* High I/O wait
* Slow application response

---

# Common Causes of High Memory Usage

1. Memory leak
2. Too many running processes
3. Large database cache
4. Java heap growth
5. Container memory exhaustion
6. Large file processing
7. Too many browser tabs (desktop systems)

# Topic 8: File Permissions & Ownership (Complete SRE Interview Guide)

> **Interview Weight:** ⭐⭐⭐⭐⭐ (Very High)

This is one of the **most frequently asked Linux topics** in SRE interviews because many production issues are caused by incorrect permissions or ownership.

Typical interview questions:

* **Why is the application getting "Permission denied"?**
* **Why is Nginx unable to read a file?**
* **Difference between 755 and 777?**
* **How do you change ownership?**
* **What are SUID, SGID, and Sticky Bit?**

---

# Why File Permissions Exist

Linux is a multi-user operating system.

Without permissions:

* Any user could delete system files.
* Any user could read confidential data.
* Any user could modify applications.

Permissions provide security by controlling access.

---

# Every File Has Three Attributes

Example:

```bash
ls -l
```

Output:

```text
-rwxr-xr-- 1 root developers 4096 Aug 3 app.sh
```

Breakdown:

```text
-rwxr-xr--
│││ │ │
│││ │ └── Others
│││ └──── Group
│└────── Owner
└──────── File type
```

---

# File Types

First character indicates the file type.

| Symbol | Type             |
| ------ | ---------------- |
| `-`    | Regular file     |
| `d`    | Directory        |
| `l`    | Symbolic link    |
| `c`    | Character device |
| `b`    | Block device     |
| `p`    | Named pipe       |
| `s`    | Socket           |

Example:

```text
drwxr-xr-x
```

This is a directory.

---

# Users, Groups, Others

Linux permissions are divided into three classes.

```text
Owner
Group
Others
```

Example:

```text
-rwxr-x---
```

Meaning:

Owner:

```text
rwx
```

Group:

```text
r-x
```

Others:

```text
---
```

---

# Permission Bits

Three basic permissions:

| Symbol | Meaning | Value |
| ------ | ------- | ----: |
| `r`    | Read    |     4 |
| `w`    | Write   |     2 |
| `x`    | Execute |     1 |

---

# Read Permission

For files:

* View contents

```bash
cat file.txt
```

For directories:

* List files

```bash
ls directory
```

---

# Write Permission

For files:

* Modify content

```bash
echo Hello >> file.txt
```

For directories:

* Create
* Delete
* Rename files

---

# Execute Permission

For files:

Run programs.

```bash
./script.sh
```

For directories:

Allows entering/traversing the directory.

```bash
cd directory
```

---

# Numeric Permissions

Linux converts permissions into numbers.

| Permission | Value |
| ---------- | ----: |
| r          |     4 |
| w          |     2 |
| x          |     1 |

Examples:

```text
rwx = 7
rw- = 6
r-x = 5
r-- = 4
```

---

# Common Permission Modes

## 777

```text
rwxrwxrwx
```

Everyone can:

* Read
* Write
* Execute

**Not recommended** for production because it is insecure.

---

## 755

```text
rwxr-xr-x
```

Owner:

```text
rwx
```

Group:

```text
r-x
```

Others:

```text
r-x
```

Common for executable scripts and directories.

---

## 644

```text
rw-r--r--
```

Owner can read/write.

Others can only read.

Common for configuration files.

---

## 600

```text
rw-------
```

Only the owner has access.

Common for SSH private keys.

Change permissions.

```bash

```

```bash

```

Remove write:

```bash

```


Recursive:

Change group only.

```bash

```

```text

```

Group:

```text
developers
```

New files and directories receive default permissions.

Check:


```text
0022
```

```text
644
```

Directories:

```text

```

# Special Permissions

Linux has three special permission bits.

1. SUID
2. SGID
3. Sticky Bit

---

# SUID (Set User ID)

Executable runs with the permissions of the file owner.

Example:

```bash
ls -l /usr/bin/passwd
```

Output:

```text
-rwsr-xr-x
```

Notice:

```text
s
```

Instead of:

```text
x
```

Why?

Changing a password requires temporary root privileges.

Set SUID:

```bash
chmod u+s program
```

Numeric:

```text
4755
```

---

# SGID (Set Group ID)

Executable runs with the group's permissions.

On directories:

New files inherit the directory's group.

Set:

```bash
chmod g+s directory
```

Numeric:

```text
2755
```

Useful for shared project directories.

---

# Sticky Bit

Common on shared directories like:

```text
/tmp
```

Permissions:

```text
drwxrwxrwt
```

The `t` means:

Users can delete **only their own files**, even if the directory is writable by everyone.

Set:

```bash
chmod +t /shared
```

Numeric:

```text
1777
```

---

# Access Control Lists (ACLs)

ACLs provide more fine-grained permissions than the standard owner/group/others model.

Check:

```bash
getfacl file.txt
```

Set:

```bash
setfacl -m u:bob:rwx file.txt
```

Remove:

```bash
setfacl -x u:bob file.txt
```

# Interview Questions

### Q1. Difference between 755 and 777?

| 755                                                      | 777                            |
| -------------------------------------------------------- | ------------------------------ |
| Owner has full access; group and others can read/execute | Everyone has full access       |
| Suitable for production executables and directories      | Generally unsafe in production |

---

### Q2. What is the difference between `chmod` and `chown`?

* `chmod` changes **permissions**.
* `chown` changes the **owner** (and optionally the group).

---

### Q3. What is SUID?

SUID allows an executable to run with the permissions of the file's owner instead of the user who launched it.

---

### Q4. What is SGID?

On executables, it runs with the file's group permissions. On directories, newly created files inherit the directory's group.

---

### Q5. What is the Sticky Bit?

On a shared directory, it prevents users from deleting or renaming files they do not own.

---

### Q6. Why does `chmod 777` create security risks?

Because any user can read, modify, or execute the file. It violates the principle of least privilege and can expose systems to accidental or malicious changes.

---

### Q7. Why can `ls` fail with "Permission denied" even if a file has `r--` permissions?

Because directory permissions also matter. To access a file by pathname, the user needs execute (`x`) permission on each directory in the path.

---

# Media.net SRE Interview Scenario

**Interviewer:** "An application reports 'Permission denied' when reading `/opt/app/config.yaml`. How would you troubleshoot?"

A strong answer:

1. Run `ls -l /opt/app/config.yaml` to check ownership and permissions.
2. Verify the application user (for example, via `ps -ef` or the service configuration).
3. Ensure the application user has read permission on the file.
4. Check execute (`x`) permission on every parent directory (`/opt`, `/opt/app`).
5. If ACLs are used, inspect them with `getfacl`.
6. Correct permissions with `chmod`, ownership with `chown`, or ACLs with `setfacl` as appropriate.
7. Test the application again and confirm the issue is resolved.
